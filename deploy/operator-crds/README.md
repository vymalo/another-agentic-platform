# aap-operator-crds

The CustomResourceDefinitions of the operator, `agentservices.agents.vymalo.com` and `agentconfigs.agents.vymalo.com` and, for
the admin dashboard (§60a), `modelendpoints.agents.vymalo.com` and `toolproviders.agents.vymalo.com` (`v1alpha1`), as a chart of
their own. A separate chart because the CRDs are installed by their own Argo CD Application in the
infrastructure project, and upgraded apart from the operator ([§59a](../../docs/architecture/10-control-plane-and-crds.md#the-operator-chart), §93).

```sh
helm template aap-operator-crds deploy/operator-crds | kubectl apply --server-side -f -
```

Server-side apply, as Argo CD's `ServerSideApply=true` sync option does: the CRDs are 67 KB, and a client-side apply keeps a copy
of the manifest in an annotation.

## One source

The CRDs are generated by `cargo run -q -p aap-operator -- crdgen > deploy/crds/agents.vymalo.com.yaml`
([`bin/operator`](../../bin/operator/README.md)). A Helm chart reads only its own directory, so this chart holds a **copy**,
[`files/agents.vymalo.com.yaml`](files/agents.vymalo.com.yaml), read with `.Files.Get` (never as a template: nothing in it is
expanded). Two checks hold the three places equal: `sh deploy/operator/tests/render-check.sh` (the copy equals
`deploy/crds/agents.vymalo.com.yaml`, and what the chart renders is that file) and the `crds-drift` job of
[`operator.yml`](../../.github/workflows/operator.yml) (it also runs `crdgen`). After a change to a type in `aap-api`:

```sh
cargo run -q -p aap-operator -- crdgen > deploy/crds/agents.vymalo.com.yaml
cp deploy/crds/agents.vymalo.com.yaml deploy/operator-crds/files/agents.vymalo.com.yaml
```

## Upgrading

**Install or upgrade the CRDs first, then the operator.** An operator from slice D2 onward expects all four CRDs (`agentservices`,
`agentconfigs`, `modelendpoints`, `toolproviders`): without the last two it no longer stalls (it watches those kinds apart, so a
list that fails holds no other agent back), but an agent whose config references a shared object stays `ConfigInvalid`, saying the
kind is not installed, until they are there. Never run an operator older than D1 against CRDs that store a reference
(`endpointRef`, `providerRef`): it types `baseUrl` as required and cannot decode such an `AgentConfig`. The other order was the
guidance of D1, when an operator read nothing new and the CRDs were the risk; for a D2 operator it is the one that leaves agents
blocked, so it is withdrawn. The CRDs over an older operator are safe as long as nobody has stored a reference: an operator from
before D1 reads every object written before it, and the Platform API of slice D5, which will write references, is not built. The
two Argo CD Applications sync apart: sequence them with the CRDs first (a sync wave, or their Application first).

The change is additive for what is stored: the `kind` job of
[`operator.yml`](../../.github/workflows/operator.yml) installs the CRDs of the commit a change builds on, stores
`examples/coder.yaml` and `examples/chat.yaml` under them, applies the new CRDs over the old and updates those objects.
The one bound on a field that existed is `tools.mcpServers`, at most 32 servers (confirmed by the owner on 2026-10-15).

## Removing it

Deleting the release deletes the CRDs, and with them every `AgentService`, `AgentConfig`, `ModelEndpoint` and `ToolProvider` (the operator's finalizers then no
longer run, so the agents' objects are left to their owner references). Nothing here keeps them (`helm.sh/resource-policy`):
protect them in the Argo CD Application (`Prune=false`, as home-os does for objects that hold data), not in the chart.
